# AGENTS.md 结构原理与写作规则

本文件解释 `<项目根>/AGENTS.md` 为什么这样写，以及写成什么样算合格。

## 1. 先定边界：它是什么

AGENTS.md 不是文档，是**约束**。三条机制决定内容该怎么组织：

| 机制 | 含义 | 写作后果 |
|---|---|---|
| 纯 Markdown、无 schema | 开放格式只规定文件名与位置，不规定字段 | 结构自行设计，唯一标准是"agent 能否照做" |
| 就近优先 | 编辑某文件时，目录树中**最近**的 AGENTS.md 生效；用户当前对话指令覆盖一切 | 根文件只放全局约定；子系统拆嵌套文件 |
| 会被**真的执行** | agent 会运行文件中列出的构建/测试/lint 命令，并修到通过 | 命令必须真实存在、可复制、幂等 |

由此推出一条判断标准：**写"新人 clone 后第一小时会问的问题"**，而不是写项目介绍。

## 2. 内容分层：价值金字塔

多数 AGENTS.md 的失败源于顺序颠倒。

```
① 可执行事实  命令、路径、版本、环境变量、入口        约 60% 篇幅
② 硬约束      必须/禁止：代码放哪、错误怎么包、生成物不可改   约 30%
③ 背景叙述    架构故事、领域概念                      约 10%，能外链就外链
```

背景叙述写多了一定稀释前两层，而 agent 对前两层的依赖远高于第三层。

## 3. 生效范围与嵌套

- 单服务仓库：根目录 `AGENTS.md`（80–180 行）+ 按主题拆到 `docs/`（每篇 20–120 行）。
- 仓库内有多个可执行产物或多个服务：根文件放全局（语言版本、提交规范、安全底线），每个服务目录再放一份写它的命令与分层。
- 前端与本服务同仓：前端目录单独一份，不把前端构建命令写进根文件。

## 4. 十二个主题放在哪

| # | 主题 | 位置 | 合格判据 |
|---|---|---|---|
| 1 | 技术栈与配置 | `docs/stack.md` | 每个选型后面有一句"为什么不能换/换的代价"，并列出环境变量清单 |
| 2 | 命令 | 根文件 | 每条命令都实测过；有明确的完成定义 |
| 3 | 分层与依赖方向 | 根文件 | 目录树 + 单向依赖 + 层职责红线 + 改动落点 |
| 4 | HTTP 约定 | `docs/api.md` | 顺序与超时写死，不留"酌情" |
| 5 | 错误与响应 | `docs/api.md` | 给出包装格式、状态码映射表、业务码取值、日志字段名 |
| 6 | 数据与迁移 | `docs/data.md` | 明确事务层级、schema 唯一来源、数据库方言约束 |
| 7 | 测试 | `docs/testing.md` | 写明怎么跑、测到什么程度、bug 先复现 |
| 8 | 安全 | `docs/security.md` | 密钥来源、校验位置、出站超时，每条都能被 review 判定 |
| 9 | 提交与 PR | 根文件 | PR 前置命令与 CI 完全相同 |
| 10 | 禁止清单 | 根文件 | 8–12 条，逐条可判定 |
| 11 | 文档索引 | 根文件 | 给出"何时读哪篇"的触发条件，而不是只列文件名 |
| 12 | 编码规范 | `docs/coding-standards.md` | 只列可判定的语言级规则；风格交给 gofmt/lint |

## 4.1 何时抽离到 `docs/`

判断标准不是"字数够多了"，而是**触发场景是否可分离**：

- 只有改某类东西时才需要读（改端点、加表、写测试）→ 抽成 `docs/` 一篇；
- 每个 PR 都要看一眼（命令、分层红线、禁止清单）→ 留在根文件；
- 抽离后必须在根文件写"何时读"索引，否则 agent 不会主动打开 `docs/`——这是抽离唯一真实的代价；
- 根文件超过 180 行、或同一份文件出现两次"只在改 X 时用得上"，就该抽了。

## 5. 写作规则

1. **预算**：根文件 80–180 行；`docs/` 每篇 20–120 行；每段 ≤ 12 行；每条一行；命令与标识符用行内代码。
   根文件超预算先抽到 `docs/`；整仓多个服务时再拆嵌套 AGENTS.md。
2. **唯一路径**：一个任务只给一种做法。禁止"也可以用 X"。
3. **可验证**：把要求写成"完成定义"（`make check` 全绿、`gofmt -l .` 无输出），而不是形容词。
4. **引用而非复制**：长文放 `docs/`，正文只留索引；避免与 README 重复。
5. **只用祈使句**：写"在 handler 层校验输入"，不写"我们通常会校验输入"。
6. **不写无法执行的命令**：没装 free 的工具、依赖不存在的目标、需要手动交互的命令，都不写。
7. **标注前提**：命令依赖 docker、cgo、make 等外部条件时，在第 2 段加"前提"列说明。
   agent 在缺少工具时会反复重试同一条命令，一次标注能省掉整轮失败。
   Go 项目的典型例子：`go test -race` 需要 cgo 与 C 工具链，Windows 本机常常没有，
   应写成"竞态检测（需 C 工具链，CI 默认执行）"，而不是伪装成默认测试命令。

## 6. 反模式

| 反模式 | 后果 | 修正 |
|---|---|---|
| 把 README 整段搬来 | 两份事实源，必然漂移 | 只保留 agent 需要的，其余留索引 |
| "写干净的代码""注意性能" | 无法判定，等于没写 | 换成具体规则（如"禁止循环内单条查询"） |
| 列出未安装的工具或过时版本 | agent 反复失败 | 删掉或写清安装方式与版本 |
| 单文件承载所有子系统 | 改 A 时被 B 的规则干扰 | 拆嵌套 AGENTS.md |
| 缺少"新代码放哪" | 目录结构逐渐失控 | 补目录树 + 归属规则 |
| 与 CI 不一致 | 本地绿、CI 红 | 命令抄自 CI 配置 |
| 罗列所有依赖的说明 | 噪声，且很快过时 | 只写选型约束与替换成本 |
| 把几百行全塞进根文件 | 每次改代码都要通读，重点被稀释 | 按触发场景抽到 `docs/`，根文件留"何时读"索引 |

## 7. 维护

- 与代码同 PR 更新：改动分层、命令、迁移流程时，同一个 PR 内改 AGENTS.md。
- 每次 CI 配置变更后核对第 2 段与第 9 段。
- 每条命令失效都是一次 agent 的失败重试，发现即修，不积累。

## 8. 交付前检查清单

- [ ] 根文件 80–180 行、`docs/` 每篇 20–120 行，每段 ≤ 12 行
- [ ] 根文件的文档索引写的是"何时读"，不是只列文件名
- [ ] 无 `{{` 占位符
- [ ] 每条命令实测通过
- [ ] Go 版本与 `go.mod` 一致
- [ ] 目录树与真实结构一致
- [ ] 与 CI 命令一致
- [ ] 禁止清单逐条可判定
- [ ] 与 README 无重复内容冲突
